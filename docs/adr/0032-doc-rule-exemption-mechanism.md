# ADR-0032　文档护栏规则的豁免清单（机器可读；覆盖 PL-032 / PL-034）

状态：**Accepted**（2026-09-18，人类指示 #1 + #11 合并裁决）　日期：2026-09-18　Supersedes：—　Superseded by：—

来源：**PL-032 / PL-034**（两条 PL 提的是**同一个问题**的不同侧面——「**新机器规则 vs 既有历史违规**」），
以及 PL-022 / ADR-0030 的同一根因（**派生事实手写多处 = 必然漂移**）。
关联：`docs/adr/0026-adr-number-registry-and-0019-collision.md` D1（ADR 编号登记表的同一原则）、
`xtask/src/memory_counts.rs` / `adr_index.rs`（机器校验的样板）、

`docs/spec/naming.md` §命名（"豁免"用词的字面量）。
PL-033（行数口径矛盾）**不在本 ADR 范围**，独立 ADR-0033 处理。

## 背景（为什么现在要决定）

新机器规则要落地时几乎总会撞上同一个坑：**仓库里已有历史违规**。把规则一上线就
flag 这些违规 = 造一条**永久红灯**；而 CI 永久红灯会让人学会忽略 CI（章程 §
与 `ci.yml` 头部注释已把这条写成设计原则）。PL-032 与 PL-034 各自独立踩到了
这个坑，必须先把**豁免机制**立起来，才能安全地把规则机器化。

### 共同的失效模式（已被本项目实证两次以上）

| 坑 | 第一次实证 | 第二次实证 | 根因 |
|---|---|---|---|
| 「同一事实手写多处必然漂移」 | PL-022：MEMORY.md 行数手算 → 永远过期 | 本轮 §1 快照里 AGENTS.md 哈希又是派生值 | 没有 SSOT，派生值随每次更新漂移 |
| 「新规则 vs 既有违规」 | PL-032：裸 ADR 引用规则=永久红灯 | PL-034：编号范围写法规则=永久红灯 | 没豁免清单，规则上线 = 红灯 = 学会忽略 CI |

### 关键发现：**豁免清单本身也是派生事实**

把豁免写在「规则实现」里（`xtask adr-index` 内部 hardcode「0021-*.md:4 豁免」）
= 重蹈 PL-022 覆辙——豁免与违规分离，每次违规消失都得改两份。
正确做法是**单独的机器可读豁免清单文件**，规则实现读它。

---

## 决策（一句话）

**把「机器规则」与「既有违规豁免」分离为两个 SSOT；豁免清单是
`docs/adr/0032-doc-rule-exemption-registry.md`，每条豁免一行
（机器可读 + 人类可读），规则的 `xtask` 实现读它。**

拆成六条：

- **D1　豁免清单的物理形态** = `docs/adr/0032-doc-rule-exemption-registry.md`，
  与本 ADR 配套；单独文件 = 规则定义与豁免列表**不耦合**。任何机器规则要
  豁免既有违规，只能来这张表里**登记一条**，不能在规则源码里 hardcode。

- **D2　每条豁免的字段（5 列固定）**：

  | 列 | 填什么 | 机器怎么读 |
  |---|---|---|
  | `ID` | `E-NNN` 顺序号 | 不读 |
  | `规则` | 机器规则的**短名**（如 `adr/bare-pending-reference`、`adr/number-range-notation`），与 xtask 规则标识符一一对应 | 必读（不匹配 = 规则对豁免"视而不见"） |
  | `位置` | `path:line`（路径相对仓库根，1-based 行号）。同一行多违规用同一 ID（如 LEDGER.md:36 同时有 0018~0025 与 0021~0026） | 必读 |
  | `理由` | 一句话——为什么豁免（如"只追加台账"、"ADR 0026 解释历史背景"、"示例文本"） | 不读（人类审计用） |
  | `移除触发` | 一句话——什么时候豁免可以摘掉（如"文件被 supersede"、"台账归档"、"模板重写"、"清单项被勾选后下次重构"）。**没有自然触发**的写"**永不（仅追加文件，无法移除）**" | 不读，但 XTASK 应在打印豁免时把"永不"的标记出来供人类季度审视 |

  **字段格式固定 = 机器可解析**（5 列 Markdown 表，机器按列号读，与
  `memory_table.rs` 的解析思路一致）。

- **D3　添加流程**（机器规则要豁免某条违规时）：
  ① 在豁免清单里**追加一行**（不删不改旧行）；
  ② 在 `decisions.md` 追加一条 `[DECISION][src:ADR-0032] 豁免 E-NNN` 记录**理由**；
  ③ （可选）若豁免涉及新机器规则的引入，该规则的实现要读这条豁免。

- **D4　移除流程**（某条豁免可以被摘掉时）：
  ① 由人类确认「移除触发」已发生；
  ② 豁免清单里该行后追加一行 `[supersedes:YYYY-MM-DD]` 标记失效（**不删原行**，
  与 `decisions.md` 的 `[supersedes]` 规矩一致）；
  ③ 实际违规可以修复时就修（如更新 LEDGER.md 的台账条目措辞）；
  ④ 规则实现下次跑时该豁免已失效 = 会重新报错 = 自然循环。

- **D5　「永不」豁免的处置**：
  豁免清单里凡是「**永不**」的条目 = 该文件是「只追加」类（LEDGER、PARKING_LOT、
  长期记忆类 ADR 正文） = 这些违规会**永远**留在仓库里。这不是 bug，是事实：
  只追加文件的语义就是不能改。XTASK 在打印豁免时应把"永不"显式标红/标 [永久]
  供人类季度审视「这些豁免还合理吗」。

- **D6　XTASK 实现的位置**：本 ADR **不实现**任何机器规则的豁免读入逻辑，
  只规定机制；实现归 PL-002 的 `xtask card-check` 与 `xtask adr-index` 的扩展
  （PL-015 一并做）。一旦实现，CI 硬门禁 #12b（doc-consistency）的 jobs 增加
  「按 ADR-0032 豁免清单跳过」的处理 = 历史违规从「永久红灯」变「白名单豁免」。

## 考虑过的选项

| # | 方案 | 结论 | 理由 |
|---|---|---|---|
| 1 | **豁免清单单独文件，机器规则读它**（本 ADR 采纳） | ✅ | 把规则定义与豁免**物理分离**，避免 PL-022 类「同一事实手写多处」。字段格式固定 = 机器可解析；[supersedes] 与「永不」两个细节把"豁免本身也是派生事实"的次生问题堵死 |
| 2 | 豁免写在每个机器规则的 xtask 源码里（hardcode） | ❌ | 重蹈 PL-022 覆辙：豁免与违规分离，每次违规消失要改两份（规则 + 豁免），且 xtask 代码动一次要重启编译 + CI；且「ADR-0019 双重占用」那种事故**正是 hardcode 编号产生的** |
| 3 | 「先全部手动修掉，再上线规则」 | ❌ | 与只追加文件的语义直接冲突（LEDGER、PARKING_LOT、ADR 正文都不能改）；且 PL-022 教我们：**等「历史清零」再上规则 = 永远等不到**；且规模上看，10 处违规要改 6 个文件、要修自然语言措辞、要保留原意 = 实质上是一个并行任务，单独排卡 |
| 4 | 「豁免不记录，规则只对新代码生效」（无豁免清单，机器只看 git log 时间戳） | ❌ | 看似简单但**测不出**"豁免了没"——机器只能判断「这是新文件还是旧文件」，不能判断「违规是哪条规则的什么变体」。PL-028 / PL-034 教我们：违规的**形态**决定豁免，git 时间戳无此信息 |
| 5 | 在 `docs/adr/README.md` §1 表格里加一列「豁免条目」 | ❌ | 登记表是关于「ADR 文件存在与否」，豁免是关于「**机器规则对哪些违规视而不见**」—— 两件事；合并会让登记表变得难读（已经 14 行了），且会让「添加豁免」与「注册 ADR」混在一起 |
| 6 | 用 `# noqa:adr/bare-pending-reference` 形式的**行内注释豁免**（同 Python 习惯） | ❌ | 这是**只追加文件不能改**的根本反命题：只追加文件里写不上注释；强行写「豁免注释」= 把「只追加」破了，与项目铁律 ⑨「不得静默扩大范围」直接冲突 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 豁免清单变成「全豁免」= 规则虚设 | ① 「永不」类显式标红 + 季度审视；② 添加豁免必须在 decisions.md 留理由（与 ADR-0028 添加锁记录的规矩一致）；③ 任何**新**违规都不会自动豁免（机器只豁免清单里登记的） |
| 豁免文件的位置漂移（重命名/移动） | 位置是 `path:line`，机器规则定位前会先确认文件存在；若文件改了，行号由 `xtask` 在跑时**重解析**该行附近的字符串（锚点）而非用行号（行号随编辑会漂）—— 这条 XTASK 实现时再定 |
| 「移除触发」到了但豁免还在 | D4 的 [supersedes] 标记 + 规则实现检查：豁免有 [supersedes] = 当成无豁免 = 重新报错 = 自然循环修复 |
| 「添加流程」被绕过（直接改规则源码塞豁免） | ① review agent 的固定检查项（gov §7.1 第 8 项）+ xtask 自检「规则源码里不允许 hardcode `ADR-0NNN` 字面量」（这种检查**也应该读 ADR-0032 豁免清单**才不冲突） |
| 豁免清单的格式漂移 | D2 固定 5 列；xtask 在解析前先 sanity-check 列数与表头（与 memory_table.rs 思路一致） |

## 验证方式（怎么知道这个决策是对的；何时应重新评估）

1. `docs/adr/0032-doc-rule-exemption-registry.md` 存在，**当前** `refscan.py` 报的
   **20** 处历史违规全部登记 = 机器跑时豁免清单的行数 ≥ refscan 的命中数；
   本轮先手算登记，refscan 命中数 − 登记数 = 0 即 PASSED。
2. `docs/adr/README.md` §1 表有 0032 行，下一可用号 0032 → **0033**（ADR-0033 处理 PL-033）。
3. `docs/memory/decisions.md` + `docs/memory/open.md` + `docs/PARKING_LOT.md` 的
   [supersedes] 链条完整（从决策源到清单到登记）。
4. **实现归 PL-002 / PL-015** 的 xtask 跑时 = 本机制真正生效 = 旧违规不再报错
   且新违规（若有人未来再加）正常报错。**这一项需要实现后才能验证**，
   属于本 ADR 的「重新评估触发条件」。
5. 重新评估触发：① 豁免条目数 > 50（清单膨胀失控）→ 拆分或缩范围；
   ② 「永不」条目数 > 80%（豁免变成默认）→ 规则本身可能被改错，需复审；
   ③ 实际违规数自然归零（所有旧文件被 supersede / 归档）→ 豁免清单可整张归档。
