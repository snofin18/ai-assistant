# ADR-0041　计划文件的「可写面」：禁止改排期与条目正文，必须实时更新完成状态

状态：**Accepted**（2026-09-24，人类 chat 澄清「禁止改 plan.md」的确切含义）　日期：2026-09-24　Supersedes：—　Superseded by：—
关联：ADR-0039（任务结束时的状态同步契约）、ADR-0031（一卡一文件）、`AGENTS.md` §8 / §11、`docs/overnight-automation-charter.md` §3

## 背景（为什么现在要决定）

`AGENTS.md` §8 与 ADR-0039 D4 把 `PLAN.md` / `plans/*` 定为 **Orchestrator 所有、Implementer 只读**；
而 ADR-0039 D1/D2 又要求**每张卡 Done 时必须在同一 PR 内**同步 `PLAN.md` 的「当前状态」块与
`README.md` 的三处。两条规则之间只靠 D4 的「唯一例外」兜着，**口径没有写全**。

2026-09-24 人类在 chat 里把口径补全（原文要点）：

> 禁止改 plan.md，说得完善一点是指：**禁止更改原有 plan 的排期以及各点要做的内容**，
> 但是**需要实时更新是否完成的状态** —— 做完的要在前面「打勾」表示完成（按定义，未必是真的打勾），
> **打勾的这段正文内容不允许修改**；同时如果有「当前进度」块，那么**这块里的内容也必须跟着进度实时更新**。

**现场后果（本次会话实测）**：`docs/overnight-automation-charter.md` §3 黑名单第 3 条**禁止**夜间 agent
修改 `PLAN.md` / `plans/*`，与 ADR-0039 D1/D2 直接冲突 → 夜间 agent 做完一张卡、走到「同步进度」步骤时
**必撞黑名单** → 记 DRIFT → 停卡。**「按计划自动逐卡推进」在机制上无法完成**，这正是本次调查要修的
阻塞项之一（另一条见 ADR-0029 的 GATE-0）。

## 决策（一句话）

计划类文件（`PLAN.md` / `plans/*`）的**可写面 = 只允许改「完成状态」与「当前进度」两类字段**；
**禁止**改排期/周期/批次顺序与各任务条目的正文；状态更新必须**实时**（与产生该状态的提交同批），
且**不得改动被标记条目的正文文本**。

## 决策细化

| # | 内容 |
|---|---|
| **D1 允许写** | ① 任务条目前的**完成标记**（`✅` / `Done` / 按该文件既有定义的形式）；② 「当前状态」/「当前进度」**块的内容**；③ **新增**任务行（新卡派单）。 |
| **D2 禁止写** | ① 排期 / 周期 / 批次顺序；② 各任务条目的**正文**（名称、write scope、验收要点、依赖、预估）；③ 已在跑的排期时刻。 |
| **D3 打勾规则** | 标记**只加在条目行首**，**不得重写条目正文**。要更正正文 → 走 `DRIFT` + 人类裁决（本 ADR 不开口子）。 |
| **D4 实时性** | 状态更新与产生该状态的提交**同批**（延续 ADR-0039 D1/D2 的「同一 PR 内」要求；**沉默跳过 = 违反铁律 1**）。 |
| **D5 授权修订** | 本 ADR **授权**修订 `AGENTS.md` §8 的 write scope 表、`AGENTS.md` §11、`docs/overnight-automation-charter.md` §3 第 3 条，使三者与本 ADR 一致。 |

## 考虑过的选项（至少 2 个，含被否理由）

| # | 选项 | 结论 | 理由 |
|---|---|---|---|
| 1 | 维持现状（计划文件对 Implementer 全只读，只有 Orchestrator 能改） | ❌ 否决 | 与 ADR-0039 D1/D2 冲突；且本次实测证明它会让**夜间自动化无法完成「同步进度」步骤** —— 护栏把正常工作挡死 |
| 2 | 计划文件全可写 | ❌ 否决 | 等于让被考核的人改考核标准（ADR-0031 D3 已否决过同一形态） |
| 3 | **只允许改「完成状态」+「当前进度」**（本 ADR） | ✅ **采纳** | 与 ADR-0039 D1/D2 一致；排期与条目正文仍受保护；人类在 chat 里给出的口径就是这一条 |
| 4 | 由 Orchestrator 单独批量同步状态 | ❌ 否决 | 依赖「记得同步」——ADR-0030 的整条动机就是「靠记得的护栏已证明会失效」 |

## 影响（需要改的 spec / 代码 / 文档 / 任务卡）

- `AGENTS.md` §8 的 write scope 表（计划文件一行的权限描述）+ §11（进度同步规则）
- `docs/overnight-automation-charter.md` §3 黑名单第 3 条（拆成「允许状态/当前进度」与「禁止排期/正文」两半）
- 后续所有任务卡的「文档同步」步骤（口径从此明确）
- **不改**：任何既有 ADR、任何任务卡的正文、任何排期

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 把「打勾」当借口顺手改条目正文 | 标记只允许加在行首（D3）→ PR diff 可逐行核对；`check-ledger`（TASK-015）上线后可加机器判据 |
| 状态更新与正文修改混在同一次提交，审阅时看不出 | 同上：diff 里「新增标记」与「改写正文」形态不同，可人工区分；本 ADR 要求审阅者**重点看 `plans/*` 的 diff** |
| 「实时」被解释成「想起来再补」 | D4 绑定「同一提交」；漏做即漂移（ADR-0039 D1/D2 已有同款判据） |

## 验证方式（怎么知道这个决策是对的；何时应重新评估）

1. **立即验证**：本 ADR 落地后，章程 §3 第 3 条与 ADR-0039 D1/D2 **不再互相矛盾** —— 人工核对两处文本；
   并在下一次夜间运行里确认 G5 → §4 步骤**不再命中黑名单**（即「卡 Done → 同步进度」这条路径走得通）。
2. **重新评估触发条件**：出现「借打勾改正文」的实际事故；或 `check-ledger` 上线后能机器判定 D3/D4 时
   （届时可把本 ADR 的 D3/D4 升级为硬门禁）。
