# ADR-0031　任务卡改为「一卡一文件」：正文与执行记录同在 `tasks/TASK-NNN-<slug>.md`

状态：**Accepted**（2026-09-18，人类裁决 DRIFT-001-3）　日期：2026-09-18　Supersedes：—　Superseded by：—

来源：**DRIFT-001-3**（原文见 `tasks/TASK-001-repo-skeleton.md` §5.3）。人类 2026-09-18 裁决：
「先做 DRIFT-001-3，按你说的一卡一文件做」。

## 背景（为什么现在要决定）

### 现象：模板要求写执行记录，但没有地方可写

gov §3.2 的任务卡模板末尾有一节 `## 执行记录（agent 填写）`，含四项（实际改动文件 /
验收输出摘要 / 偏差与 DRIFT / 遗留问题）。但本项目的卡片正文写在 `plans/stage-0-spikes.md`
（10 张卡挤在 385 行里），而 `plans/*` 对 Implementer 是**只读**（`AGENTS.md` §8）——
于是执行记录**无处可写**。TASK-001 当场新建 `tasks/TASK-001-repo-skeleton.md`（290 行）绕过，
并把这件事记成 DRIFT-001-3 等裁决。

### 为什么必须现在定，而不是留到 TASK-015

| 事实 | 后果 |
|---|---|
| `plans/stage-1-pilots.md` 只有 190 行，因为 **TASK-011~058 这 48 张卡的正文根本还没写**（目前只是批次表里的一行） | 现在是**唯一一次零迁移成本**定下卡片形态的时机。等 48 张卡的正文都写进 `plans`，那文件会上万行，再拆的成本翻几十倍 |
| DRIFT-001-3 牵动 gov §3.2 模板与**所有后续任务卡** | 越晚裁决，要回头改的卡越多；且每张新卡都会各自发明一套记录格式 |
| 人类此前已明确要求「`plan.md` 可能需要按细类拆分，方便按步的最小化读取」 | 「一卡一文件」正是按细类拆分；会话启动协议因此只需读**一个**文件 |

### 关键发现：现有文本其实已经在假定「一卡一文件」

这不是一个新发明，而是把三处**已经存在但从未写明**的假定落成规矩：

| 证据 | 原文 | 说明 |
|---|---|---|
| gov §3.2 模板的标题层级 | `# TASK-012　实现 Notepad 文本读取工具` | 是**文件级 H1**，不是 `plans` 里的一节（那应该是 `## TASK-012`）。模板整体 = 一张完整卡 + 执行记录节 = 一个文件的形状 |
| `AGENTS.md` §1 文档地图 | 「→ **你的 `tasks/TASK-NNN.md`** → `LEDGER.md` 末 10 行」 | 已经把任务卡当成 `tasks/` 下的独立文件在路由 |
| `AGENTS.md` §8 权限表 | `tasks/TASK-NNN.md`：「可填**执行记录**；**不可改 In/Out scope 与验收标准**」 | 这句话在「一卡一文件」下**逐字自洽**（正文与记录同文件，所以要划清哪半可写）；在「正文留 `plans`」下反而讲不通 —— In/Out scope 根本不在这个文件里，何来「不可改」 |

## 决策（一句话）

**任务卡改为「一卡一文件」：卡片正文与执行记录都在 `tasks/TASK-NNN-<slug>.md`，文件内用一条显式
分界线把「正文区（Orchestrator 所有，Implementer 只读）」与「执行记录区（Implementer 所有）」分开；
`plans/<阶段>.md` 退回阶段索引 —— 只留阶段级 In/Out scope、DoD、卡号索引与批次/并行建议。**

拆成七条：

- **D1　三层分工**（谁写什么、Implementer 能改什么）：

  | 文件 | 内容 | 谁写 | Implementer 权限 |
  |---|---|---|---|
  | `PLAN.md` | 全局索引（≤60 行） | Orchestrator | 只读 |
  | `plans/<阶段>.md` | **阶段级** In/Out scope、阶段 DoD、卡号索引、批次表与并行建议 | Orchestrator + 人类 | 只读 |
  | `tasks/TASK-NNN-<slug>.md` | **卡片正文**（元数据 / 目标 / In scope / Out of scope / 必须遵守 / 验收命令 / DoD）＋**执行记录**（9 节骨架） | 正文 = Orchestrator；记录 = Implementer | 记录区可写；**正文区只读** |
  | `LEDGER.md` | 一行事件（卡号 / commit / 验收结果 / 偏差） | Implementer | 只追加 |

- **D2　状态只有一个落点**：卡片的 `- 状态：` 行在 `tasks/TASK-NNN-<slug>.md` 里，
  `plans/<阶段>.md` 的卡号索引表**刻意不设「状态」列**。
  理由与 ADR-0030 完全同源：**同一个事实手写两处就必然漂移**。状态是每次会话都要改的高频值，
  若索引表也有一份，它就会在第一次忘记同步时变成谎言，而没有任何工具会报错。
  （`plans/stage-0-spikes.md` 现有的索引表本来就没有状态列 —— 这条是把既有的正确做法钉死。）

- **D3　文件内分界线**：正文区与记录区之间用一条 HTML 注释分隔，注释本身写明权限归属。
  **逐字符原文只有一处事实源 = gov §3.4**，本 ADR 刻意**不抄**一遍：抄两份就是「同一事实手写两处」
  （ADR-0030 的整条动机），而本条恰恰要求 `card-check` **按精确字符串**定位边界 —— 两份副本只要差一个空格，
  全部卡片文件就会集体解析失败。**这不是假想的风险**：本 ADR 落地时当场就抓到了三向漂移
  （草稿、gov §3.4、已迁移的 10 个卡片文件三处措辞各不相同），已统一为 gov §3.4 那一份。
  另有两条硬要求写在 gov §3.4：分界线**必须顶格**（列 0）、每文件**有且仅有一条**。

  为什么用 HTML 注释而不是 `---`：`---` 在 Markdown 里既可能是分隔线也可能把上一行变成
  setext 标题（本项目已为此设了扫描判据），而 HTML 注释在渲染后不可见、也不会与既有分隔线混淆。

- **D4　执行记录固定 9 节**（写进 gov 新增的 §3.4）：① 约束回执（`AGENTS.md` §3 的固定格式）
  ② 实际改动文件（逐个核对是否在 In scope 内）③ 验收输出摘要 ④ DoD 逐条核对
  ⑤ 偏差：none / DRIFT-0NN-x（全文按 gov §4.3 格式）⑥ 实施中发现的更合理做法（非漂移，已落地 + 理由）
  ⑦ 遗留问题（进 `PARKING_LOT` 的编号）⑧ 新增长期记忆（FACT / PITFALL / REJECTED 条目原文）
  ⑨ 给审阅者的关注点（风险最高的 1~3 处）。
  **额外收益**：第 ① 与第 ⑨ 节顺手给了**约束回执**与**完成报告**一个落盘位置 ——
  这两样东西此前只存在于聊天里，而 `AGENTS.md` 开篇就写「聊天记录不是事实源」。
  落盘之后，「回执对不对得上任务卡」这个上下文污染检测也变成了可回查的证据。

- **D5　write scope 默认项**：`tasks/TASK-NNN-*.md`（**仅本卡号那一个文件**）的**记录区**
  默认在每张卡的 write scope 内，不需要在卡里显式列出；**正文区不在**。
  这样并行 agent 之间天然不重叠（一人一卡一文件），gov §3.3 的「write scope 必须互不重叠」自动满足。

- **D6　机器判据（归 `xtask card-check`，即 PL-002）**：
  ① 正文区的 diff 非空 → **Error**（用 `git diff` 比对，机器可判）；
  ② 状态非 `Ready` 的卡必须有对应的 `tasks/TASK-NNN-*.md` 文件 → 缺失即 Error；
  ③ 记录区 9 节标题必须齐全 → 缺节即 **Warning**（不是 Error：缺节只影响可审阅性，
  不影响正确性），`Ready` 状态的卡豁免（因为它还没开工）；**早于本规定的历史记录**可用一张
  「旧格式 → 9 节」**对照表**满足本判据（详见 gov §3.4「历史记录的合规通道」）——
  **不得为过检查而改名 / 重排已提交的小节**（那是改写历史，违反「只追加不改写」）；
  ④ `plans/*.md` 里出现 `## TASK-0NN` 形态的卡片正文 → **Error**（防止迁回旧形态造成两处正文）。
  **本轮不实现**（`card-check` 至今无卡认领，PL-002），但判据先写死，避免将来重新辩论。

- **D7　命名与归档**：文件名 `tasks/TASK-NNN-<slug>.md`，`<slug>` 用 kebab-case 英文，
  且与分支名 `task/TASK-0NN-<slug>` **用同一个 slug**（便于从分支找回卡片）。
  阶段结束后把该阶段的 `tasks/*.md` 移入 `docs/history/tasks-stage-N/` ——
  与 `docs/memory/archive/` 同一精神：**按体积/阶段归档，不按时间删**。
  最终约 58+ 个文件不是问题：每个文件只在自己那张卡的会话里被读（`AGENTS.md` §1 的路由本就是单文件读取）。

## 考虑过的选项

| # | 方案 | 结论 | 理由 |
|---|---|---|---|
| 1 | **一卡一文件**（正文 + 记录同在 `tasks/TASK-NNN-<slug>.md`） | ✅ **采纳** | 与 gov §3.2 模板形态、`AGENTS.md` §1/§8 的现有措辞**逐字自洽**（见「关键发现」三条证据）；stage-1 的 48 张卡有天然落点；会话启动只读一个文件，符合人类「按细类拆分、最小化读取」的要求；并行 agent 的 write scope 天然不重叠。唯一代价（执行者技术上能改自己的考核标准）由 D3 分界线 + D6 判据 ① + review agent 三层兜住 |
| 2 | 正文留 `plans/*`、执行记录放 `tasks/`（= DRIFT-001-3 原提案） | ⚠ **次优，未采纳** | 物理隔离更彻底（执行者改不到 In/Out scope），但：① 一张卡的信息分两处，会话启动要读两个文件；② `plans/stage-0-spikes.md` 已 385 行、stage-1 的 48 张卡正文写进去会上万行；③ 需要**改** `AGENTS.md` §8 那行的措辞才讲得通（现措辞在这个方案下不自洽）。作为「不想动 `plans` 时」的退路保留 |
| 3 | 执行记录写回 `plans/*` 的卡内 | ❌ 否决 | 要把 `plans/*` 对 Implementer 开放写权限 = **让被考核的人改考核标准**，直接摧毁防漂移机制的核心；且并行 agent 必然 write scope 重叠（违反 gov §3.3）；`plans` 会迅速膨胀 |
| 4 | 只写 `LEDGER.md` + PR 描述，不落盘到卡 | ❌ 否决 | `LEDGER.md` 是「一行一事件」的流水，装不下改动清单 / 验收输出 / DRIFT 全文 / 更合理做法；PR 描述**不随 clone 传播**（本项目要开源，且合并后就没人再看）；gov §4.3 的 DRIFT 格式与 §9.4 的 PR 模板都需要一个落盘位置 |
| 5 | 新建 `docs/execution-records/` 顶层目录 | ❌ 否决 | 新顶层目录要先进 ADR 白名单（gov §5.4 第 5 项，尚未实现）；而 `tasks/` 已存在、已有 `.gitkeep` 与一个实例，复用它成本最低（同 ADR-0028 选项 3 与 ADR-0030 选项 4 的判断） |
| 6 | 卡片正文与执行记录**分成两个文件**（`tasks/TASK-NNN.md` + `tasks/TASK-NNN-record.md`） | ❌ 否决 | 物理隔离的收益与选项 2 相同，但代价更大：文件数翻倍、两者要同步卡号与 slug、`AGENTS.md` §1 的路由要写两行、review 时要开两个文件对照。选项 1 用「文件内分界线 + git diff 判据」以更低成本达到同等的可强制性 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| **执行者改自己的考核标准**（正文与记录同文件，这是本方案唯一的真实退步） | 三层：① D3 的分界线注释 + 文件头写明「正文区只读」；② D6 判据 ①「正文区 diff 非空 → Error」，机器可判；③ review agent 的固定检查项 + gov §9.4 PR 模板加一行「正文区是否被改动」。**并且要诚实承认**：这个风险在选项 2 下也没有真的消失 —— 执行者一样可以改记录来粉饰；真正拦住粉饰的是**验收命令的机器输出**，不是文件隔离 |
| 迁移把卡片正文改坏（385 行拆 10 份，纯机械操作但量大） | 迁移用脚本一次完成，**逐字节搬运正文、不改一个字**；迁移后核对「10 个文件的正文行数之和 == 原文件被移除的行数」；正文里已有的裁决修订引文（ADR-0021 / ADR-0024 等）原样保留 |
| 卡片正文与执行记录混在一个文件里，审阅时看不清改了哪半 | git diff 天然按行显示；D3 的分界线让「越界」在 diff 里一眼可见（改动出现在分界线之上即违规）；PR 模板要求写明「正文区是否被改动」 |
| 58+ 个卡片文件让 `tasks/` 变成垃圾场 | D7 的阶段归档（`docs/history/tasks-stage-N/`）；且每个文件只在自己那张卡的会话里被读，不进任何全局路由 |
| 将来有人把正文又写回 `plans/*`（形态回退） | D6 判据 ④：`plans/*.md` 里出现 `## TASK-0NN` 形态的卡片正文即 Error |
| `plans` 的索引表与卡片文件脱节（表里有卡号、文件不存在） | D6 判据 ②（状态非 Ready 的卡必须有文件）。**索引表刻意不存状态**（D2），所以「脱节」只剩「文件缺失」这一种可机器判定的形态 |

## 验证方式（怎么知道这个决策是对的；何时应重新评估）

1. `tasks/` 下有 **12** 个 `TASK-0NN-*.md`（stage-0 的 10 张 + 落地时从 `plans/stage-1-pilots.md`
   揭出并迁出的 TASK-011 / TASK-035），每个都含：元数据块（含唯一的 `- 状态：` 行）、正文区、
   D3 的分界线注释（与 gov §3.4 canonical **逐字符相等**）、记录区的 9 节标题。
   **实测结果**：12/12 通过（原型脚本 ERRORS=0 WARNINGS=0）。TASK-001 的记录区早于 9 节约定，
   按 gov §3.4「历史记录的合规通道」用一张对照表满足（不改写已提交小节）。
   ⚠ 本项**写 ADR 时预估为 10**，落地扫描才发现 stage-1 还藏着两段正文 —— 即 D6 判据 ④ 的价值在写完当天就兑现了。
2. `plans/stage-0-spikes.md` 与 `plans/stage-1-pilots.md` **都不再含**任何 `## TASK-0NN` 形态的卡片正文；仍含阶段级
   In/Out scope、DoD、卡号索引（无状态列）、并行建议、以及指向 `tasks/` 的指引表。
3. **迁移零丢失核对**：10 个卡片文件的正文行数之和 == 原 `plans/stage-0-spikes.md` 被移除的
   卡片正文行数（逐字节搬运，不含新增的元数据块 / 分界线 / 记录骨架）。核对结果记入 `LEDGER.md`。
