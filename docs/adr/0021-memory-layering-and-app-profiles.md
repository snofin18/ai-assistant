# ADR-0021　长期记忆分层：`MEMORY.md` 只做索引，细节入 `docs/memory/`

状态：Accepted　日期：2026-09-18　Supersedes：`MEMORY.md` 头部「硬上限 300 行」的单体设计　Superseded by：—
关联：`AGENTS.md` §1/§3/§5.2、`MEMORY.md`、`docs/memory/*`、ADR-0017（显式登记）、人类指示 #11（2026-09-18）

## 背景（为什么现在要决定）

`MEMORY.md` 是单体文件，设计上限 300 行，2026-09-18 已达 **256 行**。三个真实问题：

1. **读取成本与命中率不匹配**。AGENTS.md §3 要求每个会话「动手前必读 §2 §4 §5」，
   即一次性读入**全部**事实、否决项与坑（约 200 行）。而单次任务真正相关的通常只有
   2~5 条。这在阶段 0 尚可忍受，到阶段 2（Excel/Photoshop 的坑会成倍增长）就会
   挤占任务上下文 —— 本项目已因上下文问题撞过 ContextLimit（LEDGER 2026-09-17）。
2. **应用专属知识与项目级知识混在一起**。记事本的 `RichEditD2DPT`、`aid` 不唯一、
   UIA 返回裸 `\r` 等，只对 Notepad Adapter 有用，却让每个会话都付读取成本。
3. **压缩即丢失**。原设计是「超 300 行就把最老条目归档」。但记忆的价值不按时间衰减：
   2026-09-16 的「X11 会话已被移除」比 2026-09-18 的某条实测数据更长期有效。
   按时间归档会先扔掉最稳定的结论。

人类指示 #11（2026-09-18）：「memory.md 设计分层，主文件只保留必要的，其他的如有必要，
再在子文件里找，或者 codex 有好的记忆存储方式，可以尝试用起来。」

## 决策（一句话）

**`MEMORY.md` 降级为「索引 + 快照 + 指针」层（上限 150 行），全部具体条目移入
`docs/memory/` 的分层子文件；新增「应用档案」层 `docs/memory/apps/<app>.md`，
按应用维度组织事实、坑与文本约定。**

## 分层结构

```text
MEMORY.md                        ← L0 索引层（≤150 行）：快照、分工表、条目格式、
                                    各类目的指针与「何时读哪个文件」的路由规则
docs/memory/
├── README.md                    ← 路由说明（本 ADR 的落地版）
├── facts.md                     ← L1 已验证事实（FACT），按主题分节
├── pitfalls.md                  ← L1 踩坑（PITFALL），按主题分节
├── rejected.md                  ← L1 已否决方案（REJECTED）★ 动手前必读
├── decisions.md                 ← L1 决策索引（DECISION → ADR 编号）
├── open.md                      ← L1 未决（OPEN）与假设（ASSUMPTION）
├── apps/
│   ├── notepad.md               ← L2 应用档案：版本/进程模型/UIA 形状/文本约定/坑
│   ├── paint.md                 ← （TASK-003 建）
│   ├── edge.md                  ← （TASK-008 建）
│   ├── excel.md                 ← （阶段 2 建）
│   └── photoshop.md             ← （阶段 3 建）
└── archive/
    └── README.md                ← L3 归档：仅当某子文件 > 400 行时按主题拆出
```

### 读取路由（写进 `AGENTS.md` §3 启动协议）

| 你要做什么 | 读什么 |
|---|---|
| 任何工作开始前 | `MEMORY.md`（≤150 行，含快照与路由） |
| 动手前防重复辩论 | `docs/memory/rejected.md`（全量，通常最短） |
| 接某个应用 | `docs/memory/apps/<app>.md`（全量）+ `target-apps-feasibility.md` §3 对应档案 |
| 查某类事实/坑 | `docs/memory/facts.md` 或 `pitfalls.md` 的对应主题节（**grep 优先，不必全读**） |
| 查为什么这么定 | `docs/memory/decisions.md` → 对应 `docs/adr/NNNN-*.md` |
| 查还有什么没定 | `docs/memory/open.md` |

## 应用档案（`docs/memory/apps/<app>.md`）的固定小节

每个应用档案**必须**含以下小节（缺则写「未测」，不得省略标题 —— 让 agent 知道该找什么）：

1. **身份与版本**：包名/可执行文件/实测版本/安装路径/是否打包应用（MSIX）。
2. **进程与窗口模型**：进程数、窗口数、启动 PID 与窗口属主 PID 的关系、多标签/多文档结构。
   → 定位策略的唯一事实源（见 ADR-0022）。
3. **UIA 形状**：节点数、关键元素的 `ControlType`/`ClassName`/`AutomationId`/`Name`、支持的 Pattern。
4. **文本约定（`text_conventions`）**：换行表示、编码、BOM、读回校验规则、是否保留原文件 EOL。
   → ADR-0023 的每应用实例（人类指示 #2 要求的「习惯列表」）。
5. **性能实测**：遍历/定位/读写耗时（中位数 + min/max + 采样次数）。
6. **已知坑**：本应用专属 PITFALL（项目级坑仍进 `pitfalls.md`）。
7. **通道结论**：L1~L5 各通道是否可用、优先级、降级路径。
8. **未测项**：明确列出，防止把「没测」误读成「不行」。

## 为什么不用 Codex 自带的记忆机制（`~/.codex/memories/`）

人类指示 #11 提到「codex 有好的记忆存储方式，可以尝试用起来」。评估结论：**不作为事实源，仅作辅助**。

| 维度 | `~/.codex/memories/` | 仓库内 `docs/memory/` |
|---|---|---|
| 是否随仓库版本化 | ❌ 在用户目录，不进 git | ✅ 进 git，可 diff / 可 review / 可回溯 |
| 多 agent 共享（Codex/opencode/Claude Code） | ❌ 仅 Codex 可见 | ✅ 三者都读同一份 |
| 开源后可复用 | ❌ 含本机路径与隐私 | ✅ 脱敏后随仓库发布（人类指示：将来上 GitHub） |
| 与 AGENTS.md 裁决顺序的关系 | 不在裁决链内 | `MEMORY.md` 在链内（§1 文档地图） |
| 更新时机 | 需显式请求才写 | 任务卡 DoD 的一部分 |

→ **结论**：项目事实源留在仓库内；`~/.codex/memories/` 只用于「跨项目的个人偏好与本机环境备忘」，
不得承载任何项目结论。若某天它支持仓库内路径与版本化，可重新评估（登记为 `docs/memory/open.md` 一条）。

## 影响（需要改的文件）

- `MEMORY.md`：压缩为 L0 索引层；**既有 256 行内容逐条迁移，不丢条目**（迁移=复制，不重写）。
- `AGENTS.md` §1 文档地图、§3 启动协议、§5.2 `PITFALL(app=…)` 标签的汇总目标 → 改指向新结构。
  （AGENTS.md 变更需 ADR，本 ADR 即该授权。）
- `docs/memory/*`：新建 6 个 L1 文件 + `apps/notepad.md` + `archive/README.md`。
- 后续每张应用相关任务卡的 write scope 需包含对应 `docs/memory/apps/<app>.md`。

## 考虑过的选项（含被否理由）

| # | 选项 | 结论 | 理由 |
|---|---|---|---|
| 1 | 维持单体，把上限提到 600 行 | ❌ 否决 | 只推迟问题；每次会话的必读成本随文件线性增长，而命中率不变 |
| 2 | 按时间归档（原设计） | ❌ 否决 | 记忆价值不按时间衰减，会先丢最稳定的结论 |
| 3 | 全部塞进 `~/.codex/memories/` | ❌ 否决 | 不版本化、不跨 agent、不能开源（见上表） |
| 4 | 每应用一个 `MEMORY-<app>.md` 放仓库根 | ❌ 否决 | 根目录已有 20+ 文件；PL-009 正是抱怨根目录太挤 |
| 5 | **L0 索引 + L1 主题 + L2 应用 + L3 归档** | ✅ **采纳** | 读取成本与任务相关性对齐；应用知识与项目知识分离；归档按「体积」而非「时间」触发 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 分层后 agent 不知道去哪个文件找 → 记忆形同不存在 | `MEMORY.md` L0 层**必须**含路由表；`AGENTS.md` §3 启动协议显式列出必读文件 |
| 迁移过程丢条目 | 迁移用「逐条复制」而非「重写」；迁移后跑条目数核对（各 L1 文件条目总数 ≥ 原 MEMORY.md 条目数），核对结果写入 LEDGER |
| 条目同时出现在两处（L1 与 L2 重复） | 规则：**应用专属 → 只进 `apps/<app>.md`**；跨应用 → 只进 L1；L1 需要提及时写一行指针，不复制正文 |
| 子文件又长回 400+ 行 | 触发条件明确：单文件 > 400 行 → 按主题拆入 `archive/`，并在 L0 登记 |

## 验证方式

1. `MEMORY.md` ≤ 150 行且含完整路由表。
2. 原 256 行中的所有条目在 `docs/memory/` 下可 grep 到（按日期+标签抽样核对 ≥10 条）。
3. `xtask hygiene` 全绿；全仓库文件 LF、无 BOM、末尾有换行。
4. 新会话只读 `MEMORY.md` + `rejected.md` + `apps/notepad.md` 即可回答「记事本怎么定位窗口」
   —— 这是分层是否有效的真实判据（在 TASK-002 正式会话中验证）。

## 重新评估的触发条件

- 阶段 1 结束时若发现 agent 频繁「找不到已有结论」（重复踩同一个坑）→ 说明路由失败，回退到更扁平的结构。
- Codex 记忆机制若支持仓库内路径 + 版本化 + 跨 agent → 重新评估上表。
