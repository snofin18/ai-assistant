# ADR-0049　自动化最小间隔由 2.5 小时下调为 2 小时

状态：**Accepted**（2026-09-26，人类 chat 指令「都没有问题了的话，自动化搜集一下所有的运行时间，如果运行时间小于 2.5 小时，那么要给一个新的最小运行间隔时间」）　日期：2026-09-26　Supersedes：—　Superseded by：—
关联：`docs/adr/0046-automation-one-shot-instruction-driven.md` D3（本 ADR 只修订其**数值**）、`docs/overnight-automation-charter.md` §11.1 / §11.9 / §11.11 A2、`docs/nightly/codex-automations-operations.md` §4.1 / §4.1.c / §6 第 12 行、`docs/PARKING_LOT.md` PL-084 / PL-085 / PL-087、ADR-0028（guard 锁）、ADR-0029（机制）

## 背景（为什么现在要决定）

ADR-0046 D3 把「不同自动化之间的计划时刻间隔」定在 **≥ 2.5 小时（默认 3 小时）**。当时**本机还没有任何实测运行时长**，2.5 h 是按「最坏情况够用」拍出来的保守值。

2026-09-25 ~ 2026-09-26 本项目实际跑完 **7 个一次性 automation**（TASK-019 / 021 / 022 / 024 / 025 / 026 / 027），首次有了**一手运行时长**。人类据此要求：若运行时间小于 2.5 小时，就要给出一个新的最小运行间隔时间。

## 实测数据（一手；取数方法见 `docs/memory/facts.md` 2026-09-26 条）

判定方法：每个 run 的 session rollout（`~/.codex/sessions/**/rollout-*.jsonl`）第一行 `timestamp`（= run 开始）到最后一个 `event_msg.type = "task_complete"` 的 `timestamp`（= run 真正结束）之差；7 个 run 各恰好 **1 个 turn**。

| 触发（+08） | 目标卡 | 运行时长（分钟） |
|---|---|---|
| 2026-09-25 02:32:24 | TASK-019 | 50.0 |
| 2026-09-25 13:30:04 | TASK-021 | 64.1 |
| 2026-09-25 16:30:07 | TASK-022 | 40.3 |
| 2026-09-26 00:00:13 | TASK-024 | 53.4 |
| 2026-09-26 03:00:17 | TASK-025 | 28.5 |
| 2026-09-26 06:00:20 | TASK-026 | 47.6 |
| 2026-09-26 09:20:23 | TASK-027 | 39.3 |

- **7 / 7 全部成功**；**最长 64.1 分钟**（≈ 1.07 h）、中位数 47.6、均值 46.2、样本标准差 11.4。
- **全部 < 2.5 h** → 触发本次下调。
- 单侧 95% / 95% 上容限（n = 7，均值 + 4σ）≈ **92 分钟** —— 即「下一个同类 run」以约 95% 置信度不超过 ~92 分钟。

## 决策（一句话）

**把「不同自动化之间的计划时刻间隔」的下限由 2.5 小时下调为 2 小时（120 分钟）；默认值 3 小时不变。**

## 决策细化

| # | 内容 |
|---|---|
| **D1** | ADR-0046 **D3** 的**数值下限**由 **≥ 2.5 h** 改为 **≥ 2 h（120 分钟）**。ADR-0046 D3 的**其余部分**（「不同自动化之间」的定义、理由 = 杜绝两个 run 共用同一主 checkout、锁仍是必需的第二重保护）**原样继续有效**。 |
| **D2** | **默认 3 小时不变**。2 h 只是**下限**；人类给时刻时 agent 仍按「发现冲突即提示」处理（章程 §11.11 A2 的落地方式不变）。 |
| **D3** | 取值依据 = **最长实测 64.1 分钟** 的 **1.87 倍**，且**高于** n = 7 的单侧 95% / 95% 上容限（≈ 92 分钟）。**不取 1.5 h**：90 分钟（= 1.40 × 最长实测）略低于该容限，对「下一张卡更大 / 更慢」的尾部风险余量不足。 |
| **D4** | **下调不取消任何保护**：`.nightly.lock`（章程 §11.2 / G8）仍是**必需**的判据，间隔只是时间维度的概率性补充。本 ADR **不**改 ADR-0046 D1（建立需人类指令）/ D2（一次性）/ D4（内容按实际进度）。 |
| **D5** | **重新评估触发器**：任一新 run **超过 2 h**，或出现**两个 run 真的重叠** → 立即回到本 ADR 重开（改数值 = 新 ADR），并把实测写进 `docs/memory/facts.md`。 |

## 考虑过的选项（至少 2 个，含被否理由）

| # | 选项 | 结论 | 理由 |
|---|---|---|---|
| 1 | 维持 ≥ 2.5 h | ❌ 否决 | 与 7 次一手实测（最长 1.07 h）相比过度保守，且人类明确要求下调 |
| 2 | 下调为 **2 h（120 分钟）** | ✅ **采纳** | 1.87 × 最长实测，且高于 95% / 95% 上容限；取整简单、易核对 |
| 3 | 下调为 **1.5 h（90 分钟）** | ❌ 否决 | 1.40 × 最长实测，**低于** 95% / 95% 上容限（≈ 92 分钟），对更大 / 更慢的下一张卡余量不足 |
| 4 | 完全取消最小间隔，只靠 `.nightly.lock` | ❌ 否决 | 锁是**协作式**的、**无法技术强制**（ADR-0028），单靠它会回到「两个 run 抢同一主 checkout」的原始风险 |

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 某轮真的超过 2 h → 与下一轮重叠 | D5 明确触发器；`.nightly.lock` 仍是必需判据；默认 3 h 提供额外余量 |
| 样本只有 7 个，尾部未知 | D3 用「1.87 × 最长实测」+「高于 95% / 95% 上容限」双重判据；D5 要求超时即重开 |
| 数值被误当成「必须用 2 h」 | D2 明确 2 h 只是下限、默认仍是 3 h |
| 章程要求 `.nightly.lock` / 轮次产物，但**实际 prompt 里没有**（2026-09-26 复核发现：7 个 run 全部成功，但**没有一个**建过锁、**没有一个**写过 `docs/nightly/<当夜日期>-round-*.md`） | 本 ADR 授权在手册新增 **`#### 4.1.c`「prompt 固定块」**，把这两步写成可照抄的固定块；缺口同时登记为 **PL-087**（`docs/PARKING_LOT.md`） |

## 验证方式（怎么知道这个决策是对的；何时应重新评估）

1. 下一次建 automation 时，核对人类给出的时刻间隔 ≥ 2 h（D1 / D2）；
2. 继续记录每个 run 的实际时长（取数方法见 `docs/memory/facts.md` 2026-09-26 条）；
3. **何时重新评估**：任一新 run > 2 h，或两个 run 真的重叠（D5）。
